**D2 Reliability & data safety — 5.0.** This is the persona's core promise ("kick a batch before bed, trust the morning report") and it has multiple confirmed honesty holes. (a) D-17, corroborated here with a RED test: on a Redis blip the morning notification reports **$0.00** while real spend is persisted correctly one query away (`p4-priya/defects.md` — `'2/2 passes · $0.00 / $10.00 cap'` failing to contain `'$6.00'`). (c) D-06 (S1): nothing blocks an actively-subscribed user from creating a parallel Stripe subscription — live 200 + real checkout URL in `w6-stripe/_results.json` DUP-01. (d) D-07 (S2): `past_due` and pending-cancellation render zero UI difference from healthy. (e) Z12's secondary quirk: a provider-error child is marked `completed` at $0 and counted as a completed pass — a second digest-honesty hole aimed directly at this persona. Positives keeping this at 5: no prose loss observed, webhook replay genuinely idempotent (byte-identical row across replay), spend ledger user-scoped and self-consistent (0.104841675 in both `batch.spentUsd` and `digest.spentUsd`), signature verification fails closed, persona isolation 0-drift.

## 2. Defects I found in the evidence (missed or misrepresented by executors)

1. **W6 "21/21 PASS" is not supported by its own raw evidence — PRORATE-01 and PRORATE-03 are recorded `"ok": false` with `prorationLines: []` in BOTH `w6-stripe/_results.json` (lines 278–302) and `api-traces/w6-lifecycle-steps.json` (lines 352–370).** The journey log claims a corrected re-run on fresh throwaway customers whose "`prorationLines` payload [is] embedded in `_results.json` / `api-traces/w6-lifecycle-steps.json`" — it is embedded in **neither**. The quoted figures (-$49.00/+$99.00; -$99.00/+$490.00) appear nowhere in raw evidence. I re-derive the tally as **19/21 evidenced**; proration correctness is an unevidenced claim. Severity of the evidence defect: high (grading-integrity misrepresentation, whether or not the underlying product behavior is fine — Thread B is Stripe's own math, so likely a harness gap as narrated, but "likely" is not evidence).
2. **RESTORE-01 overstated:** "restored to exact original snapshot" / "byte-for-byte" — but `current_period_start`/`current_period_end` shifted ~10h48m (11:51:41.979Z → 22:39:21.813Z) in the executor's own restore trace. Shape-restore, not byte-restore; P2's billing period window was silently moved. S4 (QA hygiene), but it contradicts the PASS wording.
3. **Billing-date timezone inconsistency across surfaces (product defect, unfiled):** for the same user_qa_p4 row, `GET /api/billing/subscription` returns `currentPeriodEnd: 2026-08-16T13:51:42.005Z` (`p4-priya/api-traces/00-subscription.json`) while the raw DB row shows `2026-08-16T11:51:42.005Z` (`w6-stripe/_results.json` ISOLATION-01). Identical millisecond, 2-hour delta, both stamped `Z` — one surface mislabels local time as UTC on a billing date. Severity guess: S3.
4. **`startedAt: null` on a completed batch** (`04-batch-precancel-status.json`: `status:"done"`, `completedAt` set, `startedAt:null`). Lifecycle telemetry hole — queue-wait vs. execution time is unrecoverable, and any UI rendering start time shows nothing. Unfiled. S3/S4.
5. **Digest chapter ordering:** digest `chapters` array is ordered 2,3,4,5,6,**1** — chapter 1 last. If rendered as-is, the morning digest lists chapters out of order. S4.
6. **Z12's digest-poisoning quirk never connected to P4:** the money-path audit itself records that a provider-connection-failure child returns `success:true` → `status:'completed'` at $0 and is counted as a completed pass. That is a second "morning digest lies" pathway for precisely this persona's Return step; no executor filed it as a defect or scheduled a live probe. S2-class if it manifests.
7. **Cancel semantics untested where it matters:** the only cancel trace is against an already-done batch (`alreadyDone:true` — honest, but exercises nothing). Mid-run cancel — the control that actually protects money — has zero evidence.

## 3. "Suspiciously clean" analysis

The P4 bundle is the opposite of suspiciously clean — it self-reports worker contamination, a broken poll script, a halt order, and downgrades its own Core verdict to partial. That candor earns trust in what remains, but what remains is thin: every stress dimension of the money path (cap-hit, circuit breaker, worker-death, duplicate submission, TTL, 24-child scale, the notification Priya actually reads, raw-Redis-vs-DB ledger cross-check) is untested, and the happy-path run had 0 failures and spend at ~1% of cap — so the failure-honesty machinery this persona exists to grade was never observed live. The **W6 bundle is where the cleanliness is suspicious**: a 21/21 headline achieved by narratively converting two raw-recorded FAILs into PASSes via a "harness self-correction" whose corrected evidence is absent from the bundle, plus a "byte-for-byte restore" that isn't. Expected-but-missing across both: any UI evidence at all, any finding/manuscript content, and the live D-17 notification text.

## 4. One-line overall impression

Billing-webhook plumbing and batch-digest structure show genuinely solid bones, but the persona's defining promise — "trust the overnight money report" — carries three confirmed honesty holes (D-17 $0.00 notification, Z8 crash re-spend, D-06 parallel-subscription checkout) on top of a journey only ~20% executed and one headline PASS (proration) that its own raw evidence records as FAIL: works-but-not-yet-trustworthy, mid-5s territory overall for this lens.
