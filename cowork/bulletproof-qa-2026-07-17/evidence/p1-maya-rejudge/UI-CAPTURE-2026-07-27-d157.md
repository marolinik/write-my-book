## NEW defects observed (register-style notes; next free number was **D-169**)

**D-169 — In-thread "Keep as-is" also yanks the writer out of Editorial Review. (S2, live-proven, `43d`)**
`FindingCard`'s root `<Card>` carries `onClick={() => { setSelectedFinding(...); onShowInText?.(finding) }}`,
and on the editorial page `onShowInText` = `handleShowInText`, which does
`router.push(/books/:id/chapters/:chapterId)`. Every button *inside* `FindingCard` carefully calls
`e.stopPropagation()` (Apply, Dismiss, Discuss, Undo — `finding-card.tsx:293-348`), but the buttons
inside `FindingConversation` do **not**: "Use it", "Keep as-is" and the thread's close **X**
(`finding-conversation.tsx:52, 101-106`) pass bare `onClick={...}`. Result: dismissing from inside
the conversation both writes the PATCH *and* navigates away mid-review — the writer is dropped into
the chapter editor and loses their place in the findings queue, with no way to see the decision they
just made. Captured: `43d-keep-as-is-nav-defect.png` shows the *in-editor* findings panel (blue
selected card, `text changed` staleness badge that only `editor-findings-panel.tsx` can supply)
immediately after the click, and `43d-keep-as-is-assertions.json` shows the tell-tale
`GET …/editorial/findings?chapterNumber=1` (editor-scoped query) firing right after the PATCH.
Same bug shape hits "Use it" (accept a revision → also navigate) and the close X (dismiss the panel
→ also navigate). One-line fix per button.

**D-170 — Chip promises a memory that dismiss won't persist when a later turn carries a REVISION. (S3, source-audited + UI-corroborated in `43c`)**
`computeConversationView` scans **all** assistant turns and keeps `latestConstraint` from whichever
turn last carried one (`finding-conversation.ts:62-73`), so the chip renders. The dismiss route
re-parses **only the newest** assistant reply
(`findings/[findingId]/route.ts:267-273`, `findFirst … orderBy: { createdAt: "desc" }`). On any
thread where the writer asked for a rewrite after the editor offered to remember something — exactly
`036a088d`, visible in `43c`: turns 1–2 carry REMEMBER, turn 3 carries REVISION only — the UI shows
*On "Keep as-is", I'll remember: …* while "Keep as-is" would persist **nothing**. Same silent-drop
class as D-157 itself, one layer up: the leak is fixed, the promise is now legible, and the promise
is still breakable. Not live-fired here (would have consumed `036a088d`'s pending-state evidence);
cheap to prove — dismiss `036a088d` and diff `writer_memories`.

**D-171 — Persisted writer memories have no writer-facing surface at all. (S3, source-audited)**
`src/components/memory/writer-memory-panel.tsx` is the only component that lists / edits / revokes
`writer_memories` via `/api/memory`, and it has **zero import sites** anywhere in `src/`. The two
memory surfaces that *are* mounted — `MemorySettings` (settings page) and `MemoryStatsCard` (book
overview) — are about the Qdrant vector/RAG index (`/api/memory/stats` returns `chunkCount`,
`qdrantHealthy`, `embeddingCost`), not writer memory. Net effect: the editor tells the writer "I'll
remember X", stores X book-scoped and permanently `active`, feeds X into every later prompt via
`formatWriterMemoryForPrompt`, and the writer can never see the list, correct a mis-summarised
constraint, or take one back. The API endpoints for all three operations already exist and are
already wired in the dead panel.

**D-172 — Discuss turns are unmetered: real BYOK spend, zero `usage_records`. (S2, live-observed)**
`runDiscussTurn` (`discuss-llm.ts`) builds its own client and calls `client.messages.create` with no
usage/cost write anywhere in the discuss path (`grep` for `usageRecord|recordUsage|trackUsage` across
`src/lib/editorial/` and the editorial routes → no hits). Confirmed against the DB: the newest
`usage_records` row for this user is `2026-07-26 21:28:02` (a prior session's writing-coach call),
while this session's 24.3 s discuss turn at `23:26` recorded **nothing**. Every discuss turn is a
real charge against the writer's own OpenRouter key that the in-app spend panel will never show —
the concrete mechanism behind the D-44 / D-119 "usage panel is a dishonest health surface" family,
now pinned to a specific unbilled route.
